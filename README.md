# Churn Risk & Budget-Constrained Retention Targeting

Data Scientist take-home assignment submission — churn propensity modeling and
budget-constrained retention targeting for a subscription business.

## Data source

There is no external dataset. `customers.csv` is **synthetically generated inside the
notebook** (Section: "Data — Synthetic Generation"), using a fixed random seed
(`RANDOM_SEED = 42`) for reproducibility. Feature relationships are deliberately encoded
to mirror realistic churn drivers (low engagement, support tickets, outstanding invoices,
and competitive pressure raise churn risk; tenure and premium plan lower it), and the
generator also injects realistic imperfections — missing values, billing outliers, and
duplicate customer IDs — so the EDA and data-quality sections have genuine issues to
find rather than a clean, unrealistic dataset. Re-running the notebook from scratch will
regenerate an identical `customers.csv`.

## How to run

1. Open `Churn_Retention_Assignment_Notebook.ipynb` in Jupyter (or JupyterLab / VS Code).
2. Run all cells top to bottom (`Run All`). No external files or credentials are needed —
   the dataset is generated by the notebook itself in the first code section.
3. Runtime is under 15 seconds end-to-end on a standard laptop (20,000 rows, 3 models).

**Dependencies:** `numpy`, `pandas`, `matplotlib`, `scikit-learn`, `xgboost`.
Install with:
```
pip install numpy pandas matplotlib scikit-learn xgboost
```

The notebook is already saved with all outputs (tables, charts, printed metrics)
pre-executed, so it can also be read directly without re-running.

## Tiers completed

**All three tiers were completed:**

- **Tier 1 — Foundations:** problem framing (business/prediction/decision objectives),
  synthetic data generation, EDA, data-quality checks (missingness, outliers,
  duplicates, leakage review), and data-driven key observations.
- **Tier 2 — Modeling & Targeting:** three models trained and compared (Logistic
  Regression baseline, Gradient Boosting, XGBoost), with the best model auto-selected
  by test-set AUC; ROC curve, decile lift, and feature importance; a budget-constrained
  targeting strategy (≤30% of customers, offer cost = 20% of monthly fee) with a net
  retained revenue estimate.
- **Tier 3 — Simulation & Experimentation:** Conservative (top 10%) vs. Aggressive
  (top 30%) what-if scenarios over a 3-month revenue horizon, a sensitivity check on the
  retention-uplift assumption, and a rollout/validation plan (control-treatment test
  design, KPIs, decision gate).

## Key assumptions

All business assumptions live in a single `ASSUMPTIONS` dict inside the notebook so
they're transparent and easy to change:

| Assumption | Value | Notes |
|---|---|---|
| Max target share of customer base | 30% | Hard budget constraint from the brief |
| Offer cost | 20% of monthly fee | Per targeted customer, from the brief |
| Retention uplift from offer | 35% (relative) | **Stated assumption, not measured** — the biggest source of uncertainty in the whole analysis; the rollout plan's control/treatment test exists specifically to replace this with a real number |
| Revenue horizon (Tier 3 scenarios) | 3 months | Used to value a saved customer beyond a single billing cycle |

## Limitations

- **The dataset is synthetic.** Feature-churn relationships are realistic by
  construction, not fit to real customer behavior — the modeling pipeline is intended to
  demonstrate approach and rigor, not to produce numbers to act on directly.
- **The 35% retention-uplift assumption is unverified.** Every dollar figure in Tier 2.2
  and Tier 3 is directly proportional to this number; it should be treated as a
  placeholder for a value that would come from the recommended control/treatment test,
  not as ground truth.
- **The revenue model is simplified.** It doesn't account for partial-month churners,
  customers receiving multiple offers over time, or offer cost varying by channel — noted
  as next steps in the notebook and stakeholder summary.
- **No live drift monitoring.** The model is trained once on a static snapshot; a
  production version would need scheduled retraining and drift checks (flagged in the
  Tier 3 rollout plan).
- **1-month vs. 3-month framing is intentional, not an inconsistency.** Tier 2.2 reports
  a negative net impact over 1 month for the full 30% budget rule; Tier 3 shows the same
  rule turns positive over 3 months, and that a narrower 10% rule outperforms it further.
  This is explained explicitly in both the notebook and the stakeholder summary.
